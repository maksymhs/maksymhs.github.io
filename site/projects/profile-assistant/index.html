Ask about me

Turn a static profile into a conversation, without inventing the person behind it.

The context

Recruiters often need a specific answer: which technology appears in which role, whether the work model fits, or how experience maps to a job description. The assistant lets them ask directly, while the MCP endpoint makes that profile available to their own AI tools.

Decisions & tradeoffs

One source of professional facts

The Worker reads llms-full.txt, the same profile used by the public MCP server. Instructions tell the assistant to ground claims in that profile and disclose its AI identity.

Streamed answers with a fallback

Workers AI is tried first; OpenRouter is the configured fallback. Streaming gives the browser a response incrementally. Provider failures can still make the assistant unavailable.

Server-side credentials and boundaries

Provider credentials remain in the Worker. Chat requests are origin-checked, rate-limited and bounded by message length and conversation history. These controls do not guarantee that a model will never make a mistake.

How it fits together

  1. Visitor question
  2. Cloudflare Worker
  3. Profile + LLM
  4. Streamed answer

MCP reads the same profile through a separate public endpoint; contact delivery is a separate action.

One profile, several ways to explore it.

  • Visitors can ask questions on the site; compatible assistants can read the professional profile through the public MCP endpoint.
  • Chat, contact and MCP share one Worker implementation, with professional facts maintained in a dedicated profile file.
  • The implementation is public. No conversion, model accuracy or recruiter engagement metrics have been measured here.
